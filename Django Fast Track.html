    How Django works

    One request, start to finish. Everything else plugs into this flow.

    ~20 min

    The request/response cycle

    What happens when someone opens /movies/1/

    flowchart TD
  U["Browser"] -->|"HTTP request"| N["Nginx (web server)"]
  N --> G["Gunicorn / Uvicorn (app server)"]
  G --> H["WSGI / ASGI handler"]
  H --> M["Middleware: top to bottom"]
  M --> R["URL resolver: urls.py"]
  R --> V["View function or class"]
  V <--> O["Models / ORM"]
  O <--> DB[("Database")]
  V --> T["Template or Serializer"]
  T --> RS["HttpResponse"]
  RS --> M2["Middleware: bottom to top"]
  M2 --> U
    • Middleware wraps every request, like layers of an onion (sessions, auth, CSRF).
    • URL resolver matches the path to a view.
    • View holds the request logic. It reads or writes data through the ORM.
    • Template (HTML) or serializer (JSON) builds the output.

    MVT: Model, View, Template

    What

    Django's version of MVC. Model = data, View = logic, Template = HTML.

    Why

    Each part has one job, so code stays easy to change.

    Key point

    Django's "View" is like the MVC "Controller". Django itself (URLs + framework) does the routing.

    How

    models.py → views.py → templates/, connected by urls.py.

    Project vs app

    Project

    The whole website: settings, root URLs, WSGI/ASGI entry points.

    App

    One feature area (movies, rentals, users). It has its own models, views, URLs and tests.

    When to make a new app

    When a feature has its own data and can be explained in one sentence.

    How

    python manage.py startapp rentals, then add it to INSTALLED_APPS.

    Important files

    FileJob
    manage.pyCommand-line tool: runserver, migrate, shell, test.
    settings.pyAll configuration: apps, database, middleware, templates, static.
    urls.pyMaps URL paths to views.
    wsgi.py / asgi.pyEntry points for production servers (sync / async).
    apps.pyApp config. ready() runs once at startup (good place to connect signals).
    Watch out
    • Never use runserver in production. It is for development only.
    • App order in INSTALLED_APPS matters for templates and static files: the first match wins.

    Interview

    Explain the Django request lifecycle.

    The web server passes the request to the WSGI/ASGI handler. Middleware runs top to bottom. The URL resolver finds the view. The view uses the ORM and renders a template or serializer. The response goes back up through the middleware in reverse order.

    What is MVT and how is it different from MVC?

    Model = data, View = business/request logic, Template = presentation. Django's View does the job of the MVC Controller. The framework's URL dispatcher does the routing.

    Project vs app?

    A project is the whole site with its settings. An app is a reusable feature module. One project has many apps.

    Models and the ORM

    Python classes become tables. QuerySets become SQL.

    ~40 min

    Models, fields and relationships

    What

    A model is a Python class. One class = one table. One field = one column.

    Why

    You write Python instead of SQL. Django handles escaping, joins and different databases.

    When

    For any data you store. Use raw SQL only for rare, very complex queries.

    How

    Subclass models.Model, add fields, then run makemigrations + migrate.

    from django.db import models

class Genre(models.Model):
    name = models.CharField(max_length=100, unique=True)

class Movie(models.Model):
    title = models.CharField(max_length=255)
    genre = models.ForeignKey(Genre, on_delete=models.PROTECT, related_name="movies")
    tags = models.ManyToManyField("Tag", blank=True)
    daily_rate = models.DecimalField(max_digits=6, decimal_places=2)  # money: Decimal, not Float
    number_in_stock = models.PositiveIntegerField(default=0)
    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ["-created_at"]
        indexes = [models.Index(fields=["title"])]
        constraints = [
            models.CheckConstraint(condition=models.Q(daily_rate__gte=0), name="rate_not_negative"),
        ]

    def __str__(self):
        return self.title
    RelationshipFieldExample
    Many-to-oneForeignKeyMany movies → one genre
    One-to-oneOneToOneFieldUser → Profile
    Many-to-manyManyToManyFieldMovies ↔ Tags. Use through= when the link needs extra fields.
    on_deleteWhat happens when the parent is deleted
    CASCADEDelete the children too.
    PROTECTBlock the delete (raises an error). Safe default for important data.
    SET_NULLSet the field to NULL (needs null=True).
    RESTRICTLike PROTECT, but allows the delete if the parent is removed by another CASCADE.
    DB_CASCADE (6.1)The database does the cascade. Faster, but no Django signals run.

    QuerySets are lazy

    Chaining builds a query; it runs only when needed

    flowchart LR
  A["Movie.objects.filter(...)"] --> B[".exclude(...)"]
  B --> C[".order_by(...)"]
  C --> D{"Is the data needed?"}
  D -->|"for loop, list(), len(), bool, print"| E["ONE SQL query runs"]
  D -->|"not yet"| F["No query. Just a plan."]

    from django.db.models import Q, F, Count, Avg

Movie.objects.filter(daily_rate__gte=3, title__icontains="war")    # AND
Movie.objects.filter(Q(genre__name="Comedy") | Q(daily_rate__lt=2))  # OR with Q
Movie.objects.filter(genre__name="Drama")                            # follow a relation with __
Movie.objects.get(pk=1)              # exactly one, else DoesNotExist / MultipleObjectsReturned
Movie.objects.filter(pk=1).first()  # one or None, never raises

# F() = use a column value inside the database (no race condition)
Movie.objects.filter(pk=1).update(number_in_stock=F("number_in_stock") - 1)

# annotate = add a value PER ROW; aggregate = ONE value for the whole set
Genre.objects.annotate(movie_count=Count("movies"))
Movie.objects.aggregate(avg_rate=Avg("daily_rate"))   # {'avg_rate': Decimal('3.50')}

    Custom managers and QuerySets

    What

    Your own reusable query methods, such as Movie.objects.available().

    Why

    One place for common filters. They stay chainable.

    When

    When the same filter appears in 2+ places.

    How

    Subclass QuerySet, then use .as_manager().

    class MovieQuerySet(models.QuerySet):
    def available(self):
        return self.filter(number_in_stock__gt=0)

    def cheap(self):
        return self.filter(daily_rate__lt=2)

class Movie(models.Model):
    ...
    objects = MovieQuerySet.as_manager()

Movie.objects.available().cheap()   # chainable

    Model inheritance: 3 types

    TypeTablesUse it when
    Abstract base (abstract = True)No table for the parent. Fields are copied into each child.Shared fields such as created_at. Most common.
    Multi-tableParent and child tables, joinedRarely. Every read needs a JOIN.
    Proxy (proxy = True)Same tableSame data with different behavior, ordering or admin.
    Watch out
    • null=True is about the database (allows NULL). blank=True is about validation (allows empty in forms). For text fields, use blank=True only, and store "" instead of NULL.
    • Use DecimalField for money. FloatField gives rounding errors.
    • queryset.update() and bulk_create() skip save() and signals.

    Interview

    When is a QuerySet evaluated?

    When you iterate it, or call list(), len() or bool(), or use slicing with a step, repr() or pickling. Until then it only builds SQL. Results are cached on the QuerySet after the first evaluation.

    Difference between F() and Q()?

    F() refers to a column value inside the database (for example, add 1 to stock without loading it). Q() builds complex conditions with OR (|), AND (&) and NOT (~).

    annotate() vs aggregate()?

    annotate adds a computed value to each row and returns a QuerySet. aggregate returns a single dict for the whole set.

    get() vs filter()?

    get() returns one object and raises an error if it finds 0 or more than 1. filter() always returns a QuerySet, which can be empty.

    03

    Query performance

    The number one interview topic. Slow Django apps are almost always slow queries.

    ~35 min

    The N+1 problem

    What

    1 query for the list, then 1 extra query for each row's related object.

    Why it hurts

    100 movies = 101 queries. The page gets slower as the data grows.

    When it happens

    When a loop (in a template or serializer) accesses movie.genre or movie.tags.all().

    Fix

    select_related for FK/one-to-one; prefetch_related for many-to-many and reverse FK.

    Same page, three ways

    flowchart TB
  subgraph BAD["No fix: 1 + N queries"]
    a1["SELECT * FROM movie"] --> a2["SELECT genre WHERE id=1"]
    a2 --> a3["SELECT genre WHERE id=2"]
    a3 --> a4["... once per movie"]
  end
  subgraph SR["select_related: 1 query"]
    b1["SELECT movie JOIN genre"]
  end
  subgraph PR["prefetch_related: 2 queries"]
    c1["SELECT * FROM movie"] --> c2["SELECT tags WHERE movie_id IN (...)"]
    c2 --> c3["Python joins them in memory"]
  end

    from django.db.models import Prefetch

# FK / OneToOne -> SQL JOIN
movies = Movie.objects.select_related("genre")

# M2M / reverse FK -> second query + Python join
movies = Movie.objects.prefetch_related("tags")

# Prefetch with a custom queryset (only active rentals)
customers = Customer.objects.prefetch_related(
    Prefetch("rentals", queryset=Rental.objects.filter(returned_at__isnull=True), to_attr="open_rentals")
)

    Load less data

    ToolUse it to
    only("id", "title") / defer("plot")Load fewer columns.
    values() / values_list(..., flat=True)Get dicts or tuples instead of model objects. Faster for reports.
    exists()Check "is there any?" without loading rows.
    count()Count in SQL. Don't use len(qs) unless you need the rows anyway.
    bulk_create / bulk_updateInsert or update many rows in one query.
    iterator(chunk_size=2000)Loop over millions of rows without filling memory.
    qs.explain()See the database's query plan.

    Indexes

    What

    A sorted lookup structure, like a book index. It makes reads fast.

    Why

    Without an index, the database scans every row.

    When

    For columns used often in filter, order_by or joins. FKs get an index automatically.

    Cost

    Writes get slower and the database uses more disk. Don't index everything.

    class Meta:
    indexes = [
        models.Index(fields=["genre", "-created_at"]),           # composite: filter + sort
        models.Index(fields=["title"], condition=models.Q(number_in_stock__gt=0),
                     name="available_title_idx"),                 # partial index
    ]
    New in Django 6.1: fetch modes

    Movie.objects.fetch_mode(models.FETCH_PEERS) turns a hidden N+1 into 2 queries automatically. FETCH_RAISE raises an error on any unplanned query, which is great in development and tests to catch N+1 early.

    How to find slow queries

    • Django Debug Toolbar: shows every SQL query per page in development.
    • django-silk: profiles requests and queries.
    • Tests: assertNumQueries(2) locks the query count so N+1 can't come back.
    • Production: APM tools (Sentry, New Relic, Datadog) and the database's slow query log.
    Watch out
    • select_related on a many-to-many does nothing useful. Use prefetch_related.
    • Calling .filter() on a prefetched relation runs a new query and ignores the prefetch. Use Prefetch(..., queryset=...) instead.
    • Measure first. Don't guess.

    Interview

    select_related vs prefetch_related?

    select_related uses a SQL JOIN in one query and works for ForeignKey/OneToOne (single-valued). prefetch_related runs a separate query per relation and joins the results in Python. It works for ManyToMany and reverse ForeignKey (multi-valued).

    How do you find and fix a slow Django page?

    Measure with Debug Toolbar or an APM tool, then count queries. Fix N+1 with select/prefetch, load fewer columns, add indexes for common filters (check with explain()), cache expensive results, and move heavy work to background tasks.

    When would you use raw SQL?

    Rarely: for complex reports, database-specific features or measured hot paths. Always use parameters (raw("... WHERE id = %s", [id])), never string formatting, to avoid SQL injection.

    3. Write a test with assertNumQueries for that view.

    Version control for your database schema.

    ~25 min

    How migrations work

    From model change to database change

    flowchart LR
  A["Edit models.py"] --> B["makemigrations"]
  B --> C["New file: 0002_add_slug.py"]
  C --> D["Review + commit to git"]
  D --> E["migrate"]
  E --> F["Schema updated + row in django_migrations"]
    CommandDoes
    makemigrationsCompares the models with the last migration and writes a new file.
    migrateApplies the files that haven't run yet.
    showmigrationsLists applied [X] and pending [ ] migrations.
    sqlmigrate app 0002Shows the SQL a migration will run. Check it before big changes.

    Data migrations

    What

    A migration that changes data, not the schema.

    When

    To fill a new column, fix bad values or split a field.

    How

    makemigrations movies --empty -n fill_slugs, then add RunPython.

    Rule

    Use apps.get_model(), never a direct import. The model must match that point in history.

    from django.db import migrations
from django.utils.text import slugify

def fill_slugs(apps, schema_editor):
    Movie = apps.get_model("movies", "Movie")
    for movie in Movie.objects.filter(slug=""):
        movie.slug = slugify(movie.title)
        movie.save(update_fields=["slug"])

class Migration(migrations.Migration):
    dependencies = [("movies", "0002_movie_slug")]
    operations = [migrations.RunPython(fill_slugs, migrations.RunPython.noop)]

    Zero-downtime changes (expand and contract)

    Renaming or replacing a column safely in production

    flowchart TB
  E1["1 Expand: add new column (nullable)"] --> E2["2 Deploy code that writes both"]
  E2 --> E3["3 Backfill old rows"]
  E3 --> E4["4 Deploy code that reads new"]
  E4 --> E5["5 Contract: drop old column"]

    Why: during a deploy, old and new code run at the same time. Each step must work with both.

    Watch out
    • Never edit a migration that already ran in production. Write a new one.
    • Adding a NOT NULL column without a default, or adding an index to a huge table, can lock the table. On PostgreSQL, use AddIndexConcurrently.
    • Two developers' migrations with the same number cause a conflict. Fix it with makemigrations --merge.
    • Always commit migration files to git.

    Interview

    How do you run migrations safely in production?

    Make changes backward-compatible (expand and contract), review the SQL with sqlmigrate, avoid long table locks, run migrations as a separate step before switching traffic, and have a rollback plan.

    Schema migration vs data migration?

    A schema migration changes tables or columns. A data migration changes rows using RunPython or RunSQL, with the historical model from apps.get_model.

    Practice: Vidly Pro

    1. Add an empty slug field to Movie and migrate.
    2. Write a data migration that fills the slugs, then make the field unique=True in a third migration.
    3. Read the SQL with sqlmigrate.

    Transactions and data safety

    All or nothing. No double bookings. No lost updates.

    ~25 min

    transaction.atomic

    What

    A block of database work that fully succeeds or fully rolls back.

    Why

    If step 2 fails, step 1 must not stay saved (for example, payment saved but rental not).

    When

    Any action that writes 2 or more rows that belong together.

    How

    @transaction.atomic or with transaction.atomic():

    Race conditions and locking

    Two users rent the last copy at the same moment. Both read "stock = 1". Both rent it. Now stock is −1. Two fixes:

    from django.db import transaction
from django.db.models import F

# Fix A: lock the row until the transaction ends
@transaction.atomic
def rent_movie(customer, movie_id):
    movie = Movie.objects.select_for_update().get(pk=movie_id)   # other requests WAIT here
    if movie.number_in_stock < 1:
        raise OutOfStock()
    movie.number_in_stock -= 1
    movie.save(update_fields=["number_in_stock"])
    rental = Rental.objects.create(customer=customer, movie=movie)
    transaction.on_commit(lambda: send_receipt.enqueue(rental_id=rental.pk))
    return rental

# Fix B: one atomic UPDATE with a condition (no lock needed)
updated = Movie.objects.filter(pk=movie_id, number_in_stock__gt=0).update(
    number_in_stock=F("number_in_stock") - 1
)
if updated == 0:
    raise OutOfStock()

    on_commit: run side effects only after save

    Why emails and tasks wait for COMMIT

    sequenceDiagram
  participant V as View
  participant DB as Database
  participant Q as Task queue
  V->>DB: BEGIN
  V->>DB: INSERT rental
  V->>V: on_commit(send_receipt)
  V->>DB: COMMIT
  DB-->>V: OK
  V->>Q: send_receipt (only now)

    If you queue the task before the commit, the worker may not find the row yet, or the transaction may roll back after the email has already been sent.

    Watch out
    • ATOMIC_REQUESTS = True wraps every request in a transaction. It's simple, but it holds locks longer. Many teams prefer explicit atomic blocks.
    • Python validation is not enough. Add UniqueConstraint or CheckConstraint so the database is the final guard.
    • get_or_create can still race. Back it with a unique constraint.

    Interview

    How do you prevent two users booking the same item?

    Use select_for_update() inside atomic to lock the row, or a conditional UPDATE ... WHERE stock > 0 with F() and check the affected row count. Add a database constraint as the final guard.

    Why use transaction.on_commit?

    To run side effects (emails, tasks, cache clears) only after the data is really saved. If the transaction rolls back, they don't run.

    Practice: Vidly Pro

    1. Write rent_movie() with select_for_update.
    2. Add a CheckConstraint so stock can never go below 0.
    3. Add a UniqueConstraint: a customer can't have two open rentals of the same movie.

    paginate_by = 20

    model = Movie   # template: movies/movie_detail.html

    path("", views.MovieListView.as_view(), name="list"),

    Interview

    When FBV, when CBV?

    Use a CBV (generic views) for standard list/detail/create/update/delete pages and shared behavior through mixins. Use an FBV for unusual flows where explicit code is clearer. Both are fine; consistency within a team matters most.

    What does as_view() do?

    It returns a function that creates a new instance of the class for each request and calls dispatch(). dispatch() then calls the method matching the HTTP verb.

    Templates and forms

    Safe HTML output and safe user input.

    ~30 min

    Templates: the essentials

    • Inheritance: {% extends "base.html" %} + {% block content %}.
    • Include: {% include "partials/card.html" with movie=m %}.
    • Auto-escaping: {{ value }} is HTML-escaped, which blocks XSS. |safe turns that off, so only use it on content you trust.
    • Context processors: add variables to every template (for example request and user).
    • Custom tags and filters: put them in app/templatetags/.
    New in Django 6.0: template partials

    Define a named fragment once with {% partialdef movie-row %}…{% endpartialdef %}, reuse it with {% partial movie-row %}, or render only that piece with render(request, "movies.html#movie-row", ctx). This is great with HTMX.

    Forms

    What

    Classes that validate input and render HTML fields.

    Why

    Never trust user input. Forms clean the data, check it and report errors.

    When

    ModelForm to create or edit a model. Form for anything else (search, contact).

    How

    is_valid(), then use cleaned_data or save().

    Validation order

    flowchart TD
  A["form = RentalForm(request.POST)"] --> B["form.is_valid()"]
  B --> C["Each field: to_python, validate, validators"]
  C --> D["clean_fieldname() for each field"]
  D --> E["form.clean(): cross-field checks"]
  E --> F{"Any errors?"}
  F -->|No| G["cleaned_data, then save()"]
  F -->|Yes| H["Re-render with form.errors"]

    class RentalForm(forms.ModelForm):
    class Meta:
        model = Rental
        fields = ["movie", "rented_at", "due_at"]

    def clean_movie(self):                     # one field
        movie = self.cleaned_data["movie"]
        if movie.number_in_stock < 1:
            raise forms.ValidationError("Out of stock.")
        return movie

    def clean(self):                           # several fields
        data = super().clean()
        if data.get("due_at") and data["due_at"] <= data["rented_at"]:
            self.add_error("due_at", "Due date must be after rent date.")
        return data

    POST, Redirect, GET (PRG)

    Stops double submits on refresh

    sequenceDiagram
  Browser->>Django: POST /rentals/new (form)

    Interview

    How does CSRF protection work?

    Django sets a secret token in a cookie and requires the same token in every unsafe request (POST/PUT/DELETE), sent in a form field or header. Another site can't read the token, so it can't forge the request. CsrfViewMiddleware checks it.

    clean_<field>() vs clean()?

    clean_<field> validates one field and returns its cleaned value. clean() runs after all fields and handles rules that involve several fields.

    Users, auth and permissions

    Who are you (authentication) and what can you do (authorization).

    ~35 min

    Custom user model: do it on day one

    What

    Your own User class instead of Django's default.

    Why

    Changing the user model later is very painful, because every FK points to it.

    When

    Before the first migrate of every new project, even if it's empty.

    How

    Subclass AbstractUser and set AUTH_USER_MODEL.

    # users/models.py

    Session login flow

    Classic cookie-based login

    sequenceDiagram
  Browser->>Django: POST /login (username, password)
  Django->>Django: authenticate() checks password hash
  Django->>DB: login() creates a session row
  Django-->>Browser: Set-Cookie sessionid
  Browser->>Django: GET /rentals (cookie sent)
  Django->>Django: AuthenticationMiddleware sets request.user
    • authenticate() = check the credentials. login() = start the session. logout() = end it.
    • Passwords are stored hashed (PBKDF2 by default; Argon2 is an option), never as plain text.

    Permissions

    LevelTool
    Logged in?@login_required, LoginRequiredMixin
    Model permissionDjango auto-creates add/change/delete/view for each model. Check with user.has_perm("movies.add_movie") or PermissionRequiredMixin.
    RolesGroups: give permissions to a group (such as "Staff"), then add users to it.
    Per object ("only my rentals")Filter the queryset by request.user, or use django-guardian / django-rules, or DRF has_object_permission.
    Watch out
    • The safest object-level check is a scoped queryset: Rental.objects.filter(customer=request.user). Then other users' data can't be found at all.
    • Hiding a button is not security. Always check permissions on the server.

    Interview

    Why create a custom user model at the start?

    Swapping AUTH_USER_MODEL after tables and FKs exist needs complex manual migrations. Starting with AbstractUser costs nothing and lets you add fields later.

    AbstractUser vs AbstractBaseUser?

    AbstractUser keeps all the default fields (username, email, names) and lets you add more. AbstractBaseUser gives only the password and login logic. You define everything else and write a custom manager, for example for an email-only login.

    Authentication vs authorization?

    Authentication checks who you are (login). Authorization checks what you are allowed to do (permissions).

    Interview

    APIView vs GenericAPIView vs ViewSet vs ModelViewSet?

    APIView: you write each HTTP method yourself. GenericAPIView adds queryset, serializer and pagination helpers. ViewSet groups actions (list, retrieve) for routers. ModelViewSet = full CRUD with almost no code.

    Session auth vs JWT?

    Session auth is stateful: the server stores the session, it is easy to revoke and needs CSRF. JWT is stateless: a signed token, scales without session storage and suits mobile apps. But it is hard to revoke before it expires, so keep access tokens short-lived and use refresh tokens with rotation and a blacklist.

    How do you validate in a serializer?

    Field options (max_length, validators), validate_<field>() for one field, validate() for several fields, and model or database constraints as the final guard.

    How do you design an API for web, mobile and third parties?

    Versioned URLs, a consistent response and error format, pagination, filtering, auth that fits each client, throttling, OpenAPI docs and backward-compatible changes.

    Middleware and signals

    Hooks around every request, and hooks around model events.

    ~25 min

    Middleware

    What

    Code that runs before and after every view.

    Why

    For cross-cutting jobs: auth, sessions, CSRF, logging, request IDs, timing.

    When

    When something must happen for all requests. For a single view, use a decorator.

    How

    A class with __init__(get_response) and __call__(request), added to MIDDLEWARE.

    The onion: down on request, back up on response

    flowchart TB
  IN["Request in"] --> S1["SecurityMiddleware"]
  S1 --> S2["SessionMiddleware"]
  S2 --> S3["CsrfViewMiddleware"]
  S3 --> S4["AuthenticationMiddleware: sets request.user"]
  S4 --> V["View"]
  V -.->|"response goes back up in reverse order"| OUT["Response out"]

    import time, uuid

class RequestTimingMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response          # runs ONCE at startup

    def __call__(self, request):
        request.id = uuid.uuid4().hex              # BEFORE the view
        start = time.monotonic()
        response = self.get_response(request)     # calls the next layer
        ms = (time.monotonic() - start) * 1000     # AFTER the view
        response["X-Request-ID"] = request.id
        response["X-Response-Time-ms"] = f"{ms:.0f}"
        return response

    Optional hooks: process_view, process_exception, process_template_response. Order matters. For example, AuthenticationMiddleware needs SessionMiddleware above it.

    Signals

    What

    "When X happens, also run Y." Examples: post_save, pre_delete, user_logged_in.

    Why

    To react to events in code you don't own (third-party or Django apps).

    When to avoid

    For your own business logic. The hidden flow is hard to debug and test. Call a service function instead.

    How

    @receiver(post_save, sender=Rental), connected in AppConfig.ready().

    # users/signals.py
@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def create_profile(sender, instance, created, **kwargs):
    if created:
        Profile.objects.create(user=instance)

# users/apps.py
class UsersConfig(AppConfig):
    name = "users"
    def ready(self):
        from . import signals  # noqa: connect receivers
    Watch out
    • Signals do not fire on queryset.update(), bulk_create() or DB_CASCADE.
    • Signals run in the same transaction and thread. A slow receiver slows every save.

    Interview

    What is middleware? Give real examples.

    A layer that processes every request and response. Examples: SecurityMiddleware (HTTPS headers), SessionMiddleware, CsrfViewMiddleware, AuthenticationMiddleware (sets request.user), custom request-ID or timing middleware.

    Are signals good practice?

    Use them for decoupling from apps you don't control. Avoid them for core business logic: the flow is hidden, they're easy to break and they're skipped by bulk operations. Explicit service calls are clearer.

    Caching

    Don't compute the same thing twice. Usually done with Redis.

    ~25 min
    What

    Store a result in fast memory and reuse it.

    Why

    Fewer database hits and faster pages, so you need fewer servers.

    When

    Data that is read often, changes rarely, or is expensive to compute.

    How

    Configure CACHES (Redis is built in), then pick a level.

    Which cache level?

    flowchart TD
  Q{"What do you want to cache?"}
  Q -->|"Whole site, anonymous users"| A["Per-site cache middleware"]
  Q -->|"One full page"| B["cache_page decorator"]
  Q -->|"Part of a template"| C["cache template tag (fragment)"]
  Q -->|"Data or a query result"| D["Low-level API: cache.get / cache.set"]

    CACHES = {
    "default": {
        "BACKEND": "django.core.cache.backends.redis.RedisCache",
        "LOCATION": "redis://127.0.0.1:6379/1",
    }
}

from django.core.cache import cache
from django.views.decorators.cache import cache_page

@cache_page(60 * 5)                     # whole view, 5 minutes
def movie_list(request): ...

def top_movies():                        # cache-aside pattern
    data = cache.get("top_movies")
    if data is None:
        data = list(Movie.objects.order_by("-rentals_count")[:10].values("id", "title"))
        cache.set("top_movies", data, timeout=600)
    return data

    Cache-aside (most common)

    flowchart LR
  A["Need data"] --> B{"In cache?"}
  B -->|"Yes (hit)"| C["Return it"]
  B -->|"No (miss)"| D["Query database"]
  D --> E["cache.set with timeout"]
  E --> C

    Invalidation: the hard part

    • Timeout (TTL): simple. The data can be stale for up to N seconds.
    • Delete on change: cache.delete("top_movies") after a save (use on_commit).
    • Versioned keys: f"movie:{id}:v{updated_at}". Old keys just expire.
    • Stampede: many requests miss at once and all hit the database. Use a lock or cache.get_or_set with staggered TTLs.
    Watch out
    • Never cache pages with personal data in a shared cache by mistake. Use vary_on_cookie or cache the data only.
    • LocMemCache is per process. With 4 workers you get 4 different caches. Use Redis in production.

    Interview

    What caching levels does Django offer?

    Per-site (middleware), per-view (cache_page), template fragment ({% cache %}) and the low-level API (cache.get/set). Plus HTTP caching with ETag/Cache-Control and a CDN in front.

    How do you keep cached data fresh?

    A short TTL for data that can be a bit stale, explicit delete on write (after commit) for data that must be fresh, or versioned keys. Prevent stampedes with locks or jitter.

    Do slow work outside the request, so users don't wait.

    ~30 min
    What

    Send work to a queue. A separate worker process runs it.

    Why

    Requests stay fast, and failed jobs can retry.

    Django Tasks (6.0+) vs Celery

    Django Tasks (built-in)Celery
    API@task + .enqueue()@shared_task + .delay()

    How do you handle background jobs reliably?

    A Celery queue with a broker, idempotent tasks, retries with backoff, IDs passed (not objects), enqueue after commit, timeouts, a dead-letter or alerting process for failures, and monitoring of queue length.

    What is idempotency and why does it matter?

    Running an operation many times gives the same result as running it once. Queues deliver "at least once", so tasks can repeat. Use unique keys, status checks or database constraints to make the repeats safe.

    Async and real-time

    ASGI, async views and WebSockets: when they help and when they don't.

    ~25 min

    WSGI vs ASGI

    flowchart LR
  C["Clients"] --> S{"Server interface"}
  S -->|"WSGI: Gunicorn"| W["Sync: one request per worker thread"]
  S -->|"ASGI: Uvicorn / Daphne"| A["Async: many requests per event loop + WebSockets"]
    What

    async def views that can wait on I/O without blocking a worker.

    Why

    Many slow external calls (APIs, LLMs) can run at the same time.

    When

    I/O-heavy work, many outside calls, streaming, WebSockets.

    Not when

    Normal CRUD or CPU-heavy work. Sync is simpler and just as fast there.

    import asyncio, httpx

async def movie_ratings(request, pk):
    movie = await Movie.objects.aget(pk=pk)              # async ORM: aget, acreate, acount...
    async with httpx.AsyncClient(timeout=5) as client:
        imdb, rt = await asyncio.gather(                 # two calls at the same time
            client.get(f"https://api.example.com/imdb/{movie.slug}"),
            client.get(f"https://api.example.com/rt/{movie.slug}"),
        )
    return JsonResponse({"imdb": imdb.json(), "rt": rt.json()})

# loop over a queryset asynchronously
async for m in Movie.objects.filter(genre_id=1):
    ...

# call sync code from async code
from asgiref.sync import sync_to_async
await sync_to_async(some_sync_function)()

    Real-time with Django Channels

    • Channels adds WebSockets: chat, live notifications, dashboards.
    • Consumer = a "view" for a WebSocket connection. A channel layer (Redis) sends messages between processes.
    • Simpler option for one-way updates: Server-Sent Events (SSE) or polling.
    Watch out
    • Calling blocking code (sync ORM, requests) inside an async view blocks the whole event loop. Use async libraries or sync_to_async.
    • Under ASGI, a mix of sync and async middleware causes extra thread switching.

    Interview

    WSGI vs ASGI?

    WSGI is the synchronous standard: one request at a time per worker. ASGI is its async successor: it supports async views, long connections, WebSockets and HTTP/2. Django supports both.

    Does async make Django faster?

    Only for I/O-bound waiting, such as many outside calls at once. It doesn't speed up CPU work or simple database CRUD. Scale those with more workers, caching and query optimization.

@transaction.atomic
def rental_create(*, customer: User, movie_id: int) -> Rental:
    movie = Movie.objects.select_for_update().get(pk=movie_id)
    if movie.number_in_stock < 1:
        raise ApplicationError("Movie is out of stock.")
    movie.number_in_stock -= 1
    movie.save(update_fields=["number_in_stock"])
    rental = Rental.objects.create(customer=customer, movie=movie)
    send_receipt.delay_on_commit(rental.id)
    return rental

    Modular monolith firstSplit into microservices only when a team or scale problem really needs it.

    Interview

    How would you structure a large Django project?

    Small, focused apps with clear boundaries, split settings per environment, secrets in environment variables, a services/selectors layer for business logic, thin views and serializers, shared base models and exceptions, tests per layer, and Docker plus CI from day one.

    Where should business logic go in Django?

    Not in views, serializers or signals. Put it in services (writes) and selectors (reads), or in model methods for simple single-model rules. Then views, tasks, admin and commands can all reuse it, and you can unit-test it.

    Practice: Vidly Pro

    1. Split the settings into base/local/test/production, and move secrets to .env.
    2. Move rental logic into rentals/services.py; the API and admin action both call it.

    Interview

    TestCase vs TransactionTestCase?

    TestCase wraps each test in a transaction and rolls it back, which is fast, but on_commit callbacks don't fire unless you use captureOnCommitCallbacks. TransactionTestCase really commits and truncates the tables afterwards. It's slower, but needed for real transaction behavior.

    What is your testing approach?

    Many fast unit tests for services and selectors, API tests for each endpoint (auth, permissions, validation, query count), factories for data, mocks for external services, and everything run in CI on each pull request.

    Interview

    How does Django prevent SQL injection and XSS?

    SQL injection: the ORM sends values as query parameters, never as part of the SQL string. XSS: templates escape HTML characters in variables by default. Both break if you bypass them (raw SQL with string formatting, |safe on user input).

    What do you check before going live?

    Run check --deploy; set DEBUG off, a secret key from the environment, ALLOWED_HOSTS, HTTPS redirect, secure cookies and HSTS; protect the admin; turn on logging and error tracking; set up database backups.

    With docker-compose.yml, run web, db (Postgres), redis and worker (Celery) together locally. A common Gunicorn starting point is workers = 2 × CPU cores + 1.

    Static and media files

    Static

    Your CSS/JS/images. collectstatic copies them to STATIC_ROOT. Serve them with WhiteNoise, Nginx or a CDN.

    Media

    Files users upload. Store them in S3 or similar (django-storages), never on the container disk.

    Why

    Containers are temporary. Files saved inside them are lost on redeploy.

    Rule

    Django should not serve files in production. Let Nginx, a CDN or WhiteNoise do it.

    How to scale, step by step

    1. Measure with an APM tool and logs. Find the real bottleneck.
    2. Fix queries: N+1, indexes, only().
    3. Cache hot data in Redis; put a CDN in front of static files.
    4. Move slow work to Celery.
    5. Add app servers behind a load balancer. Django is stateless when sessions and files are kept outside the server.
    6. Scale the database: connection pooling (PgBouncer, or the Postgres pool option in Django 5.1+), read replicas, then partitioning.

    Interview

    How do you deploy Django to production?

    A Docker image runs Gunicorn (WSGI) or Uvicorn (ASGI) behind Nginx or a load balancer with HTTPS. Use Postgres, Redis for cache and broker, and Celery workers. Static files go through WhiteNoise or a CDN, media to S3. CI runs the tests, migrations run as a separate step, and Sentry and logging monitor the app.

    How do you scale a Django app?

    Measure first. Then optimize queries, add caching, move work to background tasks, scale app servers horizontally (stateless), and scale the database with pooling, replicas and partitioning.

    Static vs media files?

    Static files are part of your code (CSS/JS) and are collected at build time. Media files are uploaded by users at runtime and need persistent storage such as S3.

    The answer formula

    Use this for every question

    flowchart TB

    Rapid fire: core

    null=True vs blank=True?

    null affects the database (allows NULL). blank affects validation (allows empty input). For strings, use blank=True only.

    What are Django's main built-in protections?

    CSRF tokens, XSS auto-escaping, SQL injection-safe ORM, clickjacking headers, password hashing, ALLOWED_HOSTS and security middleware/HSTS.

    What is a context processor?

    A function that adds variables to every template context, such as request, user or messages.

    What does AppConfig.ready() do?

    It runs once when Django starts. It is used to import signal receivers and do startup setup.

    What is a manager vs a QuerySet?

    A manager (objects) is the entry point for database queries on a model. A QuerySet is the lazy, chainable query it returns. Custom QuerySet methods + as_manager() give reusable, chainable filters.

    Abstract vs proxy vs multi-table inheritance?

    Abstract: shared fields, no parent table. Proxy: same table, different Python behavior. Multi-table: separate tables joined by a one-to-one link, which is slower.

    How do you handle a ForeignKey delete?

    With on_delete: CASCADE, PROTECT, SET_NULL, SET_DEFAULT, RESTRICT, DO_NOTHING. Django 6.1 adds DB_CASCADE / DB_SET_NULL, which run in the database without signals.

    Rapid fire: ORM and performance

    What is the N+1 problem and how do you fix it?

    One query for the list plus one per row for related data. Fix it with select_related (FK) or prefetch_related (M2M/reverse), and lock it in with assertNumQueries. Django 6.1 adds FETCH_PEERS.

    How do you update a counter safely?

    update(count=F("count") + 1) runs one atomic SQL UPDATE, so there's no read-then-write race.

    How do you work with millions of rows?

    iterator() for memory, values_list for speed, bulk_create/bulk_update in batches, background tasks for long jobs, and indexes on filter columns.

    What does select_for_update do?

    It locks the selected rows (SELECT ... FOR UPDATE) until the transaction ends, so other transactions wait. It must be used inside atomic.

    Rapid fire: APIs, scale, design

    How do you secure a DRF API?

    Authentication (JWT/session), a default IsAuthenticated permission, object-level checks or scoped querysets, throttling, input validation with serializers, HTTPS only, and CORS limited to known origins.

    Which pagination would you pick for a big feed?

    Cursor pagination. It is stable while rows are added and fast, because it doesn't need large OFFSET scans.

    What's new in recent Django versions?
    • 6.0: built-in Tasks framework, Content Security Policy, template partials, BigAutoField by default, Python 3.12+.
    • 6.1: model fetch modes (FETCH_PEERS/FETCH_RAISE), database-level on_delete (DB_CASCADE), the MAILERS setting, calendar versioning (the next big release is called "Django 2028").
    • 5.2 is the current LTS (until April 2028).
    Monolith or microservices for a new Django product?

    Start with a modular monolith: clear app boundaries plus a service layer. Split out a service only for a real need (independent scaling, a separate team, a different tech stack). Microservices add network, deployment and data-consistency costs.

    Tell me about a production incident.

    Use STAR: Situation, Task, Action, Result. Cover how you detected it, debugged it (logs, metrics), fixed it, communicated, and what you changed to prevent it happening again. Show ownership and don't blame others.
